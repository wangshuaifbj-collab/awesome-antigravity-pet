# Web 性能与资源优化方案

本文记录 `codexpet.top` 的性能基线、优化决策、验收标准和回滚方式。目标是在不降低宠物展示质量、不削弱 SEO/GEO、不增加 Worker 实时读取的前提下，降低首页传输量、静态站点体积和 CI 运行成本。

## 2026-07-28 基线

| 指标                               |                    优化前 |
| ---------------------------------- | ------------------------: |
| 宠物数量                           |                       165 |
| 首页 HTML                          |                 577,096 B |
| 首页 RSC 文本                      |                 404,479 B |
| 完整宠物 JSON（紧凑格式）          |                 378,717 B |
| 首屏卡片动画估算（SSR 后随机重排） |               约 9.25 MiB |
| `web/out`                          |                约 850 MiB |
| `web/out/assets/previews`          | 约 831 MiB / 3,522 个文件 |
| 全部 GIF                           |              约 248.8 MiB |
| 全部动画 WebP                      |              约 441.5 MiB |
| 全部联系表                         |              约 124.4 MiB |
| main CI 重复生成预览               |      2 次 / 约 3 分 42 秒 |
| Web 生产依赖审计                   |       1 critical / 2 high |

统计读取已经改为部署时生成的静态 `stats.json`。普通浏览不调用 Worker，Worker 只保留安装和点赞写入。

安装链路也采用同一原则：远程安装只读取安装清单、选中的 `pet.json` 和一张
`spritesheet.webp`，不再让用户通过 npm 下载完整的 178 只宠物。安装清单包含文件大小和
SHA-256，脚本在临时目录完成校验后再原子切换；已有同一 id 的目录必须显式使用
`--force`，并且含有额外文件或符号链接的目录会被拒绝替换。npm 包只保留下载器脚本，
`npm pack --dry-run` 的包体约 26 KiB（解包约 286 KiB）；真正发布前仍需先完成 npm 发布和
不可变 commit/tag 的安装验证。

## 约束

- 首页默认随机展示，不恢复为安装量排序。
- 统计不要求实时；失败时继续展示目录，不阻塞浏览。
- 保留每只宠物的详情页完整动作预览。
- 保留 README 和 PR artifact 的动画预览与 QA 能力；生产部署不重复上传全量 QA 资源。
- 不把生成预览提交到 Git；正式宠物目录仍只包含三件套。
- sitemap、JSON-LD、`llms.txt`、`pets.json` 和索引提交继续工作。

## 实施阶段

### 阶段一：安全与交付门禁

1. 升级 Next.js 和配套 ESLint 配置，清除已知生产依赖漏洞。
2. 构建不再忽略 ESLint。
3. PR 增加 Web lint 与静态导出构建。
4. main 只生成一次全量预览；校验、构建、artifact 和部署复用同一份结果。

验收：

- `npm audit --omit=dev` 无 high/critical。
- 根目录校验、Web lint、Web build 和 Worker tests 全部通过。
- main 流水线不再在两个 job 中分别执行 `npm run previews`。

### 阶段二：首页负载

1. 为画廊建立只包含搜索、卡片和分享所需字段的 `GalleryPet`。
2. 安装命令由 slug 在客户端确定性生成，不为每只宠物重复传输长字符串。
3. Hero 在构建时从静态统计快照选出六只热门宠物，不再重复请求和排序全部宠物。
4. 卡片先显示静态缩略图，只在鼠标悬停或键盘聚焦时加载动画。
5. 客户端挂载后继续进行 Fisher-Yates 随机排序；静态缩略图避免排序前后重复下载大动画。

复杂度：

- 搜索、统计合并和排序保持 `O(n log n)`；随机洗牌为 `O(n)`。
- 客户端常驻数据由完整详情对象改为有界的画廊 DTO。
- 首页仅发起一次静态统计读取。

验收：

- 首页 HTML 和 RSC 体积显著低于基线。
- 首屏卡片默认请求缩略图，不主动请求 18 个动画。
- 随机、热门、安装、点赞和名称排序继续可用。
- 鼠标、键盘、触摸和减少动态效果设置下均可正常操作。

### 阶段三：预览与缓存

1. 网站包只复制当前目录实际引用的缩略图、动画 WebP 和 README 兼容资源。
2. 联系表和未引用的 GIF 继续留在 CI artifact，不进入 Pages 部署包。
3. README 预览统一使用动画 WebP，避免网站同时托管两套动作格式。
4. 动画 WebP 使用有损高质量编码和较高效的编码方法；先抽样验证透明度、尺寸和主观画质。
5. 为哈希静态资源、预览资源和统计快照设置分层缓存。

容量策略：

- 每只宠物的网站文件数量与动作数量线性增长。
- CI artifact 保留完整 QA 资产，但 Pages 只保留运行时资产。
- 不引入 R2；只有 Pages 包体或文件数接近平台限制时再评估对象存储。

验收：

- 部署包不包含 `contact-sheet.png` 和 `gifs/`。
- 所有 HTML、README 和公开目录引用的预览 URL 都能在 `web/out` 找到。
- 抽样动画尺寸仍为 `384x416`，帧数、持续时间和 alpha 通道正常。
- SEO 与 AI 搜索访问检查继续通过。

## 失败与回滚

- 依赖升级失败：单独回退 `web/package.json` 和锁文件，不影响数据与预览改动。
- 画廊交互回归：卡片可临时固定使用 `previewImage`；详情页完整动画不受影响。
- WebP 画质不达标：恢复无损编码参数，部署筛选和首页减重仍可保留。
- README 无法展示动画 WebP：只为 README 列出的动作恢复 GIF 复制，不恢复全部 GIF。
- 缓存导致陈旧资源：降低预览缓存时间；更新后的 HTML、catalog 和统计快照仍使用短缓存。
- 安装失败或校验不匹配：安装器不会切换临时目录；如果目标目录已有额外文件，会先报错而不是删除用户文件。需要回滚时可删除本次 pet id 目录，其他宠物目录不受影响。

## 持续观测

每次宠物数量明显增长或预览编码变化后，记录：

- 首页 HTML/RSC 字节数。
- `web/out` 总体积、文件数和预览体积。
- 前 18 张缩略图与动画的总字节数。
- CI 预览生成、构建和部署耗时。
- Worker 每日请求、有效安装、点赞和错误数。
- `npm audit`、Web lint/build、SEO 和 AI 访问检查结果。

Worker 路由迁移不是当前阶段的优先项。只有无效调用持续增长并接近免费额度时，才评估从 Custom Domain 迁移到精确匹配写入路径的 Worker Routes。

首页只传输画廊和合集所需字段，Hero 热门宠物由构建时静态快照选择。画廊和合集默认请求缩略图；画廊卡片在悬停或键盘聚焦时才切换动画。Hero 保留六只动画宠物作为首屏动态展示。

2026-07-28 时，main 流水线仍生成完整 GIF、WebP 和联系表并上传 QA artifact，但 Pages 只复制 1,541 个动作 WebP 与 165 个缩略图。新增 bundle 检查会阻止 QA 文件误入部署包，并验证公开目录引用的预览文件没有缺失。该生产 artifact 与全量生成步骤已在后续增量方案中移除，完整 QA artifact 只由有宠物变更的 PR 生成。

GitHub 官方动作已升级到原生 Node 24 的 v7，Cloudflare Wrangler Action 已升级到 v4；同时移除了强制运行时兼容开关和 Node 20 弃用警告。

## 2026-08-09 增量部署

最近一次全量生产流水线中，预览生成约耗时 5 分钟，并额外上传了 684,879,400 B 的全量预览 artifact；Cloudflare Pages 实际只上传 735 个新文件，另外 1,984 个文件已由内容哈希命中。这说明 Pages 上传本身已经是增量的，主要浪费发生在上传前的全量渲染和无条件 QA artifact。

当前部署链路改为：

1. `npm run previews:site` 只生成生产需要的缩略图和动画 WebP，不生成 GIF 与联系表。
2. 每只宠物按 `pet.json`、`spritesheet.webp`、生成器版本和输出模式计算 SHA-256 指纹；指纹一致且输出完整时直接复用。
3. GitHub Actions 按生成器/依赖哈希和全部宠物源哈希保存 `assets/previews` 缓存。新增或修改一只宠物时，从上一版缓存恢复后只重建发生变化的宠物；生成器或依赖变化会主动冷启动，避免复用不兼容结果。
4. main 不再上传约 685 MB 的生产预览 artifact。PR 仍只为发生变化的宠物生成完整 QA artifact，保留审查能力。
5. 如果源码提交会产生 README 或 catalog 自动提交，只由后续自动提交执行一次网站部署，避免两个工作流部署同一份最新 main。

本地 184 只宠物实测：冷启动站点预览生成耗时 255.36 秒；缓存全部命中时耗时 0.54 秒。CI 还需要下载并解压约 249.4 MiB 的站点预览缓存，因此实际热部署会高于 0.54 秒，但不再消耗数分钟重复编码，也不再产生全量 artifact 存储。算法会线性读取每只宠物的源文件计算指纹，时间复杂度为 `O(B + C)`，其中 `B` 是源文件总字节数、`C` 是发生变化的宠物生成成本；内存保持单只图集有界，不把全部素材同时载入内存。

失败与回滚：缓存清单损坏、缺失或输出不完整时会自动重建对应宠物；需要强制全量刷新时，提升工作流中的 `site-previews-v1` 版本或删除对应 Actions cache。回滚代码时可恢复 `npm run previews` 和 `npm run validate`，但会重新引入全量生成与大 artifact 成本。当前继续使用 Pages 静态资产，不引入 R2；只有 Actions cache 传输成为新的主要瓶颈时，才评估把预览迁移到独立对象存储。

### Next.js 与 JavaScript 缓存

三个 Web 构建路径（main、PR、手动/标签部署）现在都会缓存 `web/.next/cache`。缓存主键由操作系统、`web/package-lock.json` 和 Web 源码哈希组成；源码变化时可以恢复同一依赖版本的最近缓存，由 Next.js 自己按输入失效内部条目。`npm run build` 与 `npm run build:pr` 只清理 `.next` 中的输出并保留 `cache/`，而 `npm run clean` 仍可执行显式冷清理。该方案不缓存 `node_modules`，仍由 `npm ci` 根据锁文件重建；`actions/setup-node` 只复用 npm 下载缓存，避免牺牲可重复性。

本地缓存目录约 93 MiB。保留缓存后，当前构建的 Next.js 编译阶段由此前观测的 3.0 秒降至 1.503 秒，完整静态构建、bundle 和 SEO 校验耗时 11.97 秒。CI 还包含缓存下载和上传时间，因此收益以工作流实测为准；缓存由 GitHub Actions 的容量与淘汰策略保持有界，不建立无限增长的仓库内缓存。

浏览器端 JavaScript 原本已经使用 Next.js 内容哈希文件名和 `Cache-Control: public, max-age=31536000, immutable`。生产抽查为 Cloudflare `HIT`，因此没有把 HTML 一并设成长缓存，也没有重复创建另一套 JS 缓存。构建门禁现在会检查 `_next/static`、预览资源和 `stats.json` 三组 `_headers` 规则，防止以后改配置时悄悄丢失缓存策略。需要强制重建时运行 `npm run clean`；需要让 CI 放弃旧编译缓存时提升 `next-build-v1` 版本或删除对应 Actions cache。

## 2026-08-09 首页目录、CDN 与图片优化

### 基线与目标

本轮以 185 只宠物为规模基线：首页未压缩 HTML 约 426 KiB，完整公开宠物目录约 559 KiB，网站缩略 PNG 合计约 10.2 MiB。需求图片允许上传 5 MiB 原图，若广场列表直接引用原图，会让单张用户图片主导页面流量。

实施分为四项：

1. 首页只内联按每日随机秩选出的 18 个画廊 DTO；完整画廊改为紧凑的 `gallery.json`，搜索、筛选、非随机排序、扭蛋或滚动接近下一批时才读取。首批卡片保持客户端随机顺序，完整目录加载后只把随机化的剩余宠物追加进排名，不让已经显示的首批卡片突然跳位。
2. `pets.json`、`gallery.json`、`collections.json`、`categories.json`、`requests.json` 和 `stats.json` 使用 5 分钟浏览器缓存、10 分钟 CDN 缓存及 1 小时 stale-while-revalidate。Cloudflare 默认不把 JSON 视为可缓存扩展，因此仓库提供幂等 Cache Rule 脚本和手动工作流，只把这六个只读 GET 路径设为 eligible；HTML、API 写入和其他路径不进入规则。
3. 宠物静态缩略图从 PNG 改为 `384x416` 无损 WebP。动画 WebP、详情页动作和 PR QA 联系表不变；预览缓存格式提升版本，旧缓存不会伪装成新输出。
4. 浏览器为新上传的需求原图生成最长边 512 px 的 WebP 缩略图。Worker 仍独立校验原图，并额外限制缩略图为 WebP、最长边 512 px、400 KiB、与原图宽高比一致。原图和缩略图以原图 SHA-256 派生的不可变键分别存入 R2；广场与首页只使用托管缩略图，详情页保留原图。第三方链接不代理、不生成服务端副本，列表使用占位图，避免第三方大图、热链和 SSRF 风险。

本地生产构建实测：首页 HTML 从约 426,030 B 降至 267,921 B，减少约 37.1%；按需目录为 156,160 B。185 张新 WebP 缩略图合计约 6.81 MiB，对比旧 PNG 约 10.22 MiB，减少约 33.4%。最终导出 2,735 个文件、278.7 MiB，其中 1,944 个动作预览占 247.6 MiB，说明后续若继续压缩部署体积，应优先处理动作预览，而不是再次压缩已经较小的目录 JSON。

### 复杂度与容量

- 首页首屏常驻画廊对象从 `O(n)` 降为固定 18 个；完整目录只在需要时进行一次 `O(n)` 校验、去重和合并。搜索保持 `O(n)`，排序保持 `O(n log n)`，并发目录请求合并为一个 Promise。
- `gallery.json` 是独立、紧凑、可缓存资源。目录数量上限在客户端验证为 5,000，异常或超时不会替换首批静态内容。
- WebP 缩略图生成仍按宠物线性处理，内存上限为单张图集。R2 每次请求最多新增一个原图和一个有界缩略图，不建立无限内存缓存。
- 上传总请求上限包含 5 MiB 原图、400 KiB 缩略图和表单余量。Turnstile、每日一次的 IP 限制、格式签名、像素上限和内容哈希键继续生效。

### 部署与回滚

- 首次启用 JSON 边缘缓存时，手动运行 `Configure Cloudflare CDN cache`。API Token 需要 `Zone > Cache Rules > Edit`，可选配置 `CLOUDFLARE_ZONE_ID`；脚本只按固定描述更新自己的规则，不覆盖其他 Cache Rules。
- Cache Rule 不可用时，`_headers` 的浏览器缓存仍有效，网站正确性不依赖边缘命中。回滚时删除该固定描述规则即可，不需要清除 HTML。
- 完整目录加载失败时保留首批 18 只宠物；筛选结果可能暂时不完整，但不会阻塞首页其他内容。
- 不支持 WebP Canvas 编码的旧浏览器会阻止文件上传并显示现有失败文案，用户仍可切换公开链接模式。已有的 R2 请求在缩略图尚未回填时可以临时回退到原图；第三方链接和绕过标准表单的新请求在列表显示占位图，详情页仍可查看原图。
